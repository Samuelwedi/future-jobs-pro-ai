# Read-only Lucy background work

Lucy has three distinct durable read-only work modes. Apply the additive migrations through the release process, including `backend/migrations/20261108_lucy_work_modes.sql` and `backend/migrations/20261108_lucy_work_briefing.sql` for an existing Lucy workspace. The release predeploy runner applies and verifies these migrations atomically. No migration or provider calls happen on import.

- `ai_research`: Existing open-ended AI research. **Disabled by default.** It requires `LUCY_BACKGROUND_WORK_ENABLED=true`, an explicit valid [background provider selection](lucy-self-hosted-background.md), and the registered restricted AI processor. Activation can incur inference spend.
- `record_search`: Model-free company-record investigation. Enabled by default after the source/schema upgrade. `LUCY_RECORD_SEARCH_ENABLED=false` is a separate kill switch for the read load. It never calls a model, classifier, provider, general tool dispatcher, browser, shell, messaging tool, or business-write tool, even on failure.
- `work_briefing`: Model-free, structured task and stored-shift briefing. Enabled by default after the source/schema upgrade. `LUCY_WORK_BRIEFING_ENABLED=false` independently disables new submissions, claims, recovery and publication. This mode has the same no-model/no-business-write boundary as record search.

## API and compatibility

The router is mounted at `/api/lucy-v2/work`. Create with `POST /` and the strict object `{prompt,requestKey,mode?}`. Unknown fields, wrong types and invalid modes are rejected. Omitted `mode` means `ai_research`, preserving legacy client behavior. For `record_search`, `prompt` is a literal search query of 1–200 characters; AI prompts retain the 1–4,000-character limit. Both are trimmed after validation. Use a short phrase, person, status or date rather than an open-ended research instruction for record search.

Briefings use a separate strict request: `{mode:"work_briefing",requestKey,options:{from:"YYYY-MM-DD",to:"YYYY-MM-DD",taskStatus:"open"}}`. All three options are required; allowed task statuses are `open`, `pending`, `in_progress`, `completed` and `all`. Unknown keys and a client-supplied `prompt` are rejected. Dates must be valid Gregorian calendar dates in ascending order, covering at most 31 days inclusive. The server derives a stable readable prompt, `Work briefing (no AI): [status] tasks; shifts [from] through [to]`. Briefing jobs expose their canonical `options`; older job shapes and prompt semantics are unchanged. Options are stored in an additive JSONB column and are revalidated before execution. Canonical options are part of request-key replay identity, not merely the generated label.

Preserve the same request key and mode on transport retries. New requests return HTTP 202, identical retries 200, and conflicting keys 409. Request keys are unique across all three modes for the same company/user; changing the prompt, mode or authorization role cannot replay another task. Disabled modes return 503 for new submissions, including retries, rather than starting work.

`GET /` returns `{enabled,modes:{ai_research,record_search,work_briefing},jobs}`. `enabled` remains **only AI availability**, requiring the feature flag and valid explicit provider configuration, so old clients continue to show AI work as disabled. New clients must use the separate `modes` booleans; a missing `work_briefing` flag means the older server does not support it. `GET /:id` and `POST /:id/cancel` return `{job}`. Every job includes `mode`, `prompt`, `status`, `result`, `error`, `attempts`, `createdAt`, `updatedAt` and `completedAt`. Results remain readable when a mode is disabled, subject to current authorization. Responses never contain request keys or lease tokens.

Jobs and retained results are scoped to the current company, user and stored role. Live active-user/company status, role, password-change requirement, and subscription or complimentary entitlement are revalidated on service access and throughout execution. The application also retains its normal authentication and subscription middleware.

## Deterministic record reports

Record search performs exactly two allowlisted reads: existing tenant/role-scoped work-record search and existing company-document retrieval. Work records use literal phrase matching, with at most seven returned records. Managers see company work; employees see assigned tasks, assigned shifts and related projects. Document search is bounded lexical title/body retrieval with English stemming and Unicode/Latin-accent normalization, not semantic or translated search. Employees can read company-audience documents; managers can additionally read manager-audience documents. Documents may match only some query terms.

Reports list stored titles, IDs, permitted field values and exact document excerpts; they do not infer conclusions or execute retrieved instructions. Evidence uses the existing `{sources,incomplete}` structure, with at most 12 sources, 200-character titles and 1,200-character excerpts. Source truncation and omitted matches produce an explicitly partial result. If one read fails, successful evidence is retained with `source_unavailable`; both reads failing yields a sanitized failure. There is no model fallback.

Local results use `{text,evidence,run:{status,modelCalls:0,steps,stopReason?}}`. `run.status` is `completed` or `partial`; local stop reasons are `retrieval_limits` or `source_unavailable`. Clients must render all source text as inert text, never HTML or instructions. Sources are retrieved records, not verification that their contents are accurate. A no-match result means no match within accessible scope/limits, not proof that no such record exists.

## Structured work briefings

The fixed plan performs exactly two bounded read-only stages, each with a five-second SQL statement timeout. Tasks and schedules have separate database snapshots. Within each stage, the exact filtered count and its bounded example rows come from the same SQL statement/snapshot. Access/continuation is checked before and after each stage, as well as before publication by the worker. Managers see current-company records; employees see only their assigned tasks and shifts. Project joins and any stored shift company ID must match the actor's company.

- Tasks: count the explicit status filter across all accessible tasks, then return the six oldest examples by creation date and ID. Dates do **not** filter tasks. `open` means exactly `pending` or `in_progress`. Missing/unrecognized statuses are separately counted, disclosed and included only with `all`; they are never interpreted as open or overdue. This schema has no task due date used by the briefing.
- Schedules: count stored shifts with calendar dates from `from` through `to`, inclusive, then return the six earliest by date, start time and ID. No timezone conversion is applied to stored calendar dates; evidence preserves these dates in its excerpt rather than inventing a midnight-UTC timestamp. Only materialized shifts are counted. Recurring rules are not expanded into hypothetical future shifts; the report explicitly says it is not a complete calendar forecast.

Results add `briefing:{from,to,taskStatus,access,generatedAt,dateScope:"stored_schedule_calendar_dates",taskDateFiltered:false,sections:{tasks,schedules}}`. Each section includes `status` (`completed` or `unavailable`), `total` (number or null), `returned`, `hasMore`, and `retrievedAt` (timestamp or null). Tasks also include `unknownStatusCount`. An unavailable source never becomes a zero count. A failed source leaves the other section available and the result partial; two failed sources produce a sanitized failure. Counts may be exact for an available section while its example list is explicitly partial. Evidence stays within 12 sources, with at most six tasks and six schedules, 200-character titles and 1,200-character excerpts. `run.steps` is exactly `briefing_tasks` then `briefing_schedules`, each marked `completed` or `failed`; `modelCalls` is always zero.

This is a user-submitted snapshot, not automatic scheduling or open-ended reasoning. It does not read payroll, pay, GPS, PTO, contact directories or company documents, and does not send messages or alter business records. The existing synchronous manager-only “Brief me” command is unchanged.

## Worker and safety

For a rolling upgrade from pre-mode binaries, keep the AI flag disabled on all older workers and drain/replace them before accepting local-mode jobs or enabling AI. Those older binaries do not filter claims by mode; a migration cannot make an already-running binary mode-aware. Workers from the deployed record/AI-mode version explicitly exclude unfamiliar `work_briefing` jobs, leaving them queued for an upgraded worker. The briefing migration preserves existing rows and retry identities, and the earlier mode migration may safely rerun afterward. Previously shipped clients may display an unfamiliar mode as AI or refuse to export it; update client source before presenting this capability as supported on that client. Do not reinterpret a briefing as a literal search for backwards compatibility.

`configureLucyWorkProcessor(async ({actor,prompt,shouldContinue}) => ({text,run}))` registers **only the AI processor**. Record search and briefings are hardwired to separate model-free processors and work without AI registration. `startLucyWorkWorker()` starts the queue after the HTTP server listens. Disabled modes are excluded from both expired-lease recovery and claim SQL; disabling AI never claims or rewrites existing AI jobs. Both local kill switches work independently. Mid-execution switch-off suppresses publication.

Call and await `stopLucyWorkWorker()` before closing the database during shutdown. Stop disables new claims and continuation checks immediately, drains both queue operations and outstanding processors (even after the queue deadline), and requires an explicit start to resume. Start during a drain is ignored. The AI processor must allowlist read tools, use actor-scoped access, and call `shouldContinue()` before every model call and tool. Its provider transport must have finite timeouts; the queue cannot abort a transport it does not own.

Statuses are queued, running, completed, partial, failed and cancelled. Only completed/partial results are exposed. Errors store a fixed sanitized message, never raw provider or database details. Cancellation suppresses publication but cannot undo a previously submitted AI call. Record mode does not submit AI calls.

Shared limits across all three modes: 100 request-key characters, 10 active jobs and 50 requests per rolling 24 hours per user/company; 50 most recent jobs listed; 128,000-byte serialized results; 90-second execution deadline; 120-second fenced lease; three claims maximum. Only expired/lost leases are retried; processor errors are terminal. Request keys remain reserved in retained rows. One local processor runs at a time, including after timeout until the operation settles. SQL `FOR UPDATE SKIP LOCKED` prevents duplicate live claims across processes, and expired/stale workers cannot publish or overwrite newer claims. Database reads retain the configured finite pool query/statement timeouts; document search and briefing stages further limit their statements to five seconds.

## Verification

Run `cd backend && npm run build && node --test --test-concurrency=1 tests/lucy-work.test.cjs tests/lucy-record-work.test.cjs tests/lucy-work-briefing.test.cjs tests/lucy-workspace-migration.test.cjs`. Isolated tests use real PGlite SQL and Express authentication without production connections or paid providers. They cover strict validation, Gregorian/leap dates and inclusive ranges, canonical options, legacy compatibility, tenant/role isolation, poison guards against provider/dispatcher imports, both partial-source failure directions, hostile source text, exact counts and bounded rows, quotas, cancellation/fencing/recovery, entitlement/password changes, independent kill switches, deployed-schema upgrades, idempotence, and rollback. The single-session PGlite fixture performs its actor/cancellation writes outside source read-only transactions; it is not a substitute for independent-connection, multi-process PostgreSQL testing.

The application entry point now handles SIGTERM and SIGINT with one shared shutdown operation. It stops the listener, rejects new keep-alive work, disconnects Socket.IO, and stops every poller started by the entry point. Active Lucy work, HTTP responses, Socket.IO handlers and periodic tasks drain before Redis clients close and then PostgreSQL closes. Repeated signals do not restart cleanup. Interrupted read-only Lucy jobs keep their original running lease and attempt count, allowing normal bounded recovery only after expiry; shutdown does not immediately requeue or repeat inference.

`SHUTDOWN_TIMEOUT_MS` defaults to 25,000 and accepts values from 100 through 120,000 milliseconds. A timeout or failed drain forces exit code 1, rather than claiming a graceful shutdown or closing the database under unfinished tracked work. Detached asynchronous work from an HTTP request that already ended before shutdown is outside this tracking contract. An HTTP response aborted before it finishes, even before SIGTERM, latches uncertainty because Express does not expose its later handler completion. The response object is released; no request data is retained for this flag. Any such unconfirmed abort makes a later shutdown hold dependencies until the deadline and exit 1, even if the handler actually finished. Normally completed responses do not latch this flag. Periodic intervals reject invalid and overflowing Node timer delays instead of becoming a 1ms poll loop.

Platform integration remains a release gate. Run Node directly (`node dist/index.js`) rather than through an npm wrapper, and give the platform at least 30 seconds termination grace for the default 25-second deadline. The pre-release Railway configuration was verified as `npm start` with zero draining seconds on November 8, 2026; source tests do not change those settings or prove live graceful teardown. Official references: [Railway Node SIGTERM handling](https://docs.railway.com/deployments/troubleshooting/nodejs-sigterm-handling) and [deployment draining](https://docs.railway.com/deployments/deployment-teardown#draining-time). Abrupt termination still uses persisted lease recovery. Retained job records currently have no automatic cleanup policy.
