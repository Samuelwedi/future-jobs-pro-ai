# Read-only Lucy background work

This additive source upgrade is **off by default**. Apply the separately reviewed `backend/migrations/20261108_lucy_background_work.sql` through the release process, register the restricted processor, and explicitly set `LUCY_BACKGROUND_WORK_ENABLED=true` before starting processing or accepting new requests. No migration or provider calls happen on import. Enabling processing may incur inference spend.

Mount the default `lucyWorkRoutes` router at `/lucy-v2/work`. It uses existing `companyActor` authentication. Create with `POST /` and `{prompt,requestKey}`; preserve the same request key on transport retries. New requests return HTTP 202, retries 200, conflicting keys 409. `GET /` returns `{enabled,jobs}`, `GET /:id` and `POST /:id/cancel` return `{job}`. Jobs are scoped to the current company and user, including stored role for retained-result reads. Responses never contain request keys or lease tokens.

Configure `configureLucyWorkProcessor(async ({actor,prompt,shouldContinue}) => ({text,run}))` before calling `startLucyWorkWorker()`. Call and await `stopLucyWorkWorker()` before closing the database during shutdown. Stop disables new claims and continuation checks immediately, drains both queue operations and outstanding processors (even after the queue deadline), and requires an explicit start to resume. Start calls during a drain are ignored. A processor that never settles will hold shutdown open, so configure finite provider transport timeouts. The processor must only permit explicitly allowlisted read tools, use actor-scoped data access, revalidate authorization and call `shouldContinue()` before **every model call and every tool**. Never expose shell, browser, arbitrary-code execution, or business mutations. The queue is not a capability boundary for an unsafe processor. Model/provider calls should have their own short request timeouts; the queue cannot abort a provider transport it does not own.

Statuses are queued, running, completed, partial, failed and cancelled. The processor's `run.status==='partial'` produces partial, never completed. Polling clients must display the actual status. Only completed/partial results are exposed. Provider failures store a fixed sanitized message, not raw errors. Cancellation suppresses publication but cannot undo an already submitted inference call.

Limits: 4,000 prompt characters, 100 request-key characters, 10 active jobs and 50 requests per rolling 24 hours per user/company; 50 most recent jobs listed; 128 KB serialized results; 90-second execution deadline; 120-second fenced lease; three claims maximum. Only lost/expired leases are retried; provider errors are terminal. Request keys remain reserved in retained rows. A local worker runs one processor at a time, even if the processor outlives the deadline. SQL `FOR UPDATE SKIP LOCKED` prevents duplicate live claims across processes. Expired workers cannot publish or overwrite newer claims. Role/company changes and deactivation fail closed.

Run isolated tests: `cd backend && npm run build && node --test tests/lucy-work.test.cjs`. Tests use real in-memory PGlite SQL and Express authentication; only the injected processor is mocked. They do not contact a production database or inference provider. PGlite verifies claim SQL and separate worker instances, but does not substitute for a multi-process PostgreSQL load test.

The current application registers the restricted processor and starts this worker after its HTTP server begins listening. The service-level drain API is tested, but comprehensive application SIGTERM/SIGINT draining is not wired here; abrupt process termination recovers through persisted leases. Verify deployment shutdown/restart behavior before enabling processing. The existing provider adapter has finite transport timeouts. Retained job records currently have no automatic cleanup policy.
