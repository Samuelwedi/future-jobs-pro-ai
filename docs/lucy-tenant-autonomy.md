# Lucy tenant autonomy: next safe increment

Reviewed release: `71ec27a0b62f34c9754c9a2dfbf4effcb475040c` in `/workspace/shared/future-jobs-pro-ai-lucy`. The baseline design review was source inspection only and its working tree was clean. A separately authorized prerequisite implementation followed in a separate worktree; see the implementation addendum below for its exact scope and proof. No provider calls, production database access, cloud changes, migrations, deployments, or native builds were performed. Links below are derived from the checkout's GitHub origin and exact commit, not a claim of live deployment verification.

## Decision for implementation

Ship **one model-free, durable task-status action** in Lucy first. A customer employee can update a task currently assigned to them; a customer manager can update a task in their company. The authenticated customer's explicit action request is sufficient by default. No Samuel approval, model call, support-owner token, provider purchase, or native build is involved. Add stricter organization policy only where that organization chooses it. Keep research queues read-only.

Do not interpret this as full general-purpose autonomous Lucy. This slice delivers one real customer operation with durable execution/history and lays the write boundary needed for subsequent tools. It must not advertise external actions, autonomous payroll payment, code repair, or unrestricted natural-language execution.

## Source-linked findings, in priority order

1. **There is no Samuel-personal approval gate in current customer execution.** Synchronous `create_task` already inserts for the manager-role group; `request_pto` already inserts for the signed-in user. Payroll draft preparation requests that user's own confirmation and checks the proposal company. [Customer writes and payroll](https://github.com/Samuelwedi/future-jobs-pro-ai/blob/71ec27a0b62f34c9754c9a2dfbf4effcb475040c/backend/src/routes/lucyJarvisRoutes.ts#L212-L261). Customer authority and Samuel's permission to incur provider spend/build Android or iOS are different domains. Neither approval can replace the other.
2. **PTO has an actual validation bypass.** Lucy uses its own direct INSERT with only date-pattern/order checks. The existing `validatePTORequest`/`createPTORequest` service enforces real dates, permitted types, a 366-day range, active company membership and serialized overlap checks. Lucy bypasses these. [Lucy PTO](https://github.com/Samuelwedi/future-jobs-pro-ai/blob/71ec27a0b62f34c9754c9a2dfbf4effcb475040c/backend/src/routes/lucyJarvisRoutes.ts#L220-L225), [PTO service](https://github.com/Samuelwedi/future-jobs-pro-ai/blob/71ec27a0b62f34c9754c9a2dfbf4effcb475040c/backend/src/services/ptoService.ts#L33-L67). Fix before claiming Lucy executes the same business rules as the UI.
3. **Role checks do not fully guarantee record scope.** `manages` accepts `boss, owner, manager, admin`, while task/PTO/approval routes omit `owner`. Generic Lucy `projects` returns every company project to an employee while `searchLucyWork` limits projects to assigned-shift or time-entry relationships. Lucy task/shift/time/GPS joins do not consistently assert the related user's/project's company; PTO reads scope via current user membership rather than also `pr.company_id`. The direct task POST accepts an unchecked `assigned_to`, so bad cross-company references are not merely hypothetical schema damage. [Role helper](https://github.com/Samuelwedi/future-jobs-pro-ai/blob/71ec27a0b62f34c9754c9a2dfbf4effcb475040c/backend/src/middleware/companyActor.ts#L4-L10), [Lucy reads](https://github.com/Samuelwedi/future-jobs-pro-ai/blob/71ec27a0b62f34c9754c9a2dfbf4effcb475040c/backend/src/routes/lucyJarvisRoutes.ts#L148-L209), [task POST/PATCH](https://github.com/Samuelwedi/future-jobs-pro-ai/blob/71ec27a0b62f34c9754c9a2dfbf4effcb475040c/backend/src/routes/taskRoutes.ts#L45-L92), [scoped search](https://github.com/Samuelwedi/future-jobs-pro-ai/blob/71ec27a0b62f34c9754c9a2dfbf4effcb475040c/backend/src/services/lucyWorkSearch.ts#L11-L32). Static findings, not a live exploit test. No database RLS policy was found in the reviewed migrations; do not assume one supplies missing predicates.
4. **The request ledger is a useful replay fence, not action authorization or an atomic write receipt.** An absent requestId returns `untracked`. A present ID binds company/user/role plus message/language/channel hash and permanently reserves the key; failed final persistence must not cause reexecution. Business writes are separate transactions and can commit before the final reply. No cancellation endpoint or claim check exists immediately inside each mutation transaction. [Ledger semantics](https://github.com/Samuelwedi/future-jobs-pro-ai/blob/71ec27a0b62f34c9754c9a2dfbf4effcb475040c/backend/src/services/lucyRequestService.ts#L101-L175), [chat invocation](https://github.com/Samuelwedi/future-jobs-pro-ai/blob/71ec27a0b62f34c9754c9a2dfbf4effcb475040c/backend/src/routes/lucyJarvisRoutes.ts#L327-L383). Retain legacy tombstones; never reinterpret an uncertain request as safe to retry.
5. **Prompt instructions are not a permission fence.** Runtime validates flat arguments, filters available tools and deduplicates identical writes within a run. It does not prove that the authenticated user's current message authorized a proposed mutation. Only company-document and work-record searches taint a run as read-only; `tasks`, `projects`, `schedules` and other reads also return user-controlled text but do not trigger that fence. A source can therefore influence a later write, subject to the prompt rather than an intent check. [Runtime](https://github.com/Samuelwedi/future-jobs-pro-ai/blob/71ec27a0b62f34c9754c9a2dfbf4effcb475040c/backend/src/services/lucyAgentRuntime.ts#L72-L99), [tool configuration](https://github.com/Samuelwedi/future-jobs-pro-ai/blob/71ec27a0b62f34c9754c9a2dfbf4effcb475040c/backend/src/routes/lucyJarvisRoutes.ts#L371-L389). Do not add new model-invoked mutation tools in this increment.
6. **Background work has strong read-only controls, unsuitable for writes by extension alone.** It revalidates membership, role, entitlement and password policy; uses 120-second fenced leases; checks cancellation; and retries expired read leases up to three times. Cancel removes results, appropriate for research but wrong for committed writes. [Queue](https://github.com/Samuelwedi/future-jobs-pro-ai/blob/71ec27a0b62f34c9754c9a2dfbf4effcb475040c/backend/src/services/lucyWorkService.ts#L97-L168), [read-only processor](https://github.com/Samuelwedi/future-jobs-pro-ai/blob/71ec27a0b62f34c9754c9a2dfbf4effcb475040c/backend/src/routes/lucyJarvisRoutes.ts#L409-L432). Keep the current three modes unchanged.
7. **Current activity records are not authoritative receipts.** `recordAction` best-effort inserts a title/status/summary and swallows errors; no request/action ID or structured target linkage is stored there. `ops_actions` demonstrates same-transaction business result + replay record, but its manager-only wrapper is not a general employee-capability/entitlement verifier. [Lucy activity](https://github.com/Samuelwedi/future-jobs-pro-ai/blob/71ec27a0b62f34c9754c9a2dfbf4effcb475040c/backend/src/routes/lucyJarvisRoutes.ts#L23-L25), [operations action](https://github.com/Samuelwedi/future-jobs-pro-ai/blob/71ec27a0b62f34c9754c9a2dfbf4effcb475040c/backend/src/services/operationsCore.ts#L12-L22).
8. **Payroll confirmation should not be copied as the new generic approval framework.** It identifies the latest per-user proposal, not an explicit action hash; role lists differ; proposal and generator transactions are separate; catch restores `pending` after a generator/approval-write error that may have committed payroll. The generator does guard duplicate company/date payroll and locks approved time entries, so this is an atomicity/reconciliation gap, not a claim of unbounded duplicate payroll. Draft generation changes/locks timesheets even though it never pays. [Customer confirmation](https://github.com/Samuelwedi/future-jobs-pro-ai/blob/71ec27a0b62f34c9754c9a2dfbf4effcb475040c/backend/src/routes/lucyJarvisRoutes.ts#L227-L261), [approval API](https://github.com/Samuelwedi/future-jobs-pro-ai/blob/71ec27a0b62f34c9754c9a2dfbf4effcb475040c/backend/src/routes/approvalRoutes.ts#L35-L59), [generator](https://github.com/Samuelwedi/future-jobs-pro-ai/blob/71ec27a0b62f34c9754c9a2dfbf4effcb475040c/backend/src/services/payrollGenerator.ts#L11-L57).

## Concrete action / role / approval matrix

“Manager group” means the explicit shared helper's boss/owner/manager/admin roles, not support-agent roles. Fix aliases on the touched paths, not by silently elevating unknown roles. Every action additionally requires active current-company membership and active subscription/trial/valid complimentary entitlement.

| Action | Current released behavior | Customer authority / target constraint | Next increment approval behavior |
|---|---|---|---|
| Work records and documents | Chat and model-free/read-only jobs | Employee assigned tasks/shifts/related projects and company-audience docs; managers company scope and manager docs | No approval. Make direct reads consistent with scoped search. No write authorization derived from results. |
| Workforce/time/PTO/GPS/payroll summaries | Chat reads; some background research | Self where applicable; GPS/payroll/financial company views manager-only | No approval beyond access checks; preserve field minimization. |
| Create task | Synchronous Lucy write | Manager group; assignee active in the same company, or unassigned | Existing explicit customer request; no Samuel gate. Harden common task service/receipts before queued expansion. |
| Change task status | UI PATCH exists, no Lucy tool | Manager group current-company task OR employee currently assigned that task; exact ID/status | First new Lucy action. Execute explicit request by default; org policy may deny or require customer confirmation. |
| Request PTO | Synchronous Lucy INSERT; UI service safer | Signed-in user only; company scope, valid dates/type, no overlap | Submission completes automatically on valid explicit request; leave remains pending under company PTO approval. Submission is not approval of leave. |
| Prepare payroll draft | Customer proposal plus clear confirmation | Manager group; exact tenant/pay period and currently approved unlocked entries | Keep explicit customer confirmation. Exclude from new write lane until payload-bound atomic approvals are built. No payroll payments. |
| Invoice labor preview | Read-only proposal | Manager group; tenant project, exact dates and rate | No issued/sent invoice. Existing Operations draft confirmation remains. Do not count preview as completed invoice creation. |
| PTO/timesheet approval, schedule edits, bulk changes | Not Lucy adapters reviewed here | Separate domain permissions and conflict rules | Not in first action registry. Do not infer permission merely because user is a manager. |
| External messages, purchases, payroll funding, taxes | No Lucy customer executor | Dedicated policies and financial/compliance gates needed | Deny in this lane. Customer policy cannot unlock an absent executor. |
| Organization Lucy policy | No existing dedicated policy found | New explicit `manage_lucy_policy` capability, initially tenant boss/owner/admin; manager excluded by default | Authenticated settings change, versioned and audited. No model policy tool. Admin is tenant-scoped, never platform owner. |
| Support diagnosis, code repair, tests/build/deploy/store submission | Separate support-owner system | Dedicated support authentication and release authority | Never available to customer action registry. Customer tenant-owner role is not support-owner role. |
| Provider spending / Android or iOS builds | Operator/development authorization domain | Samuel's relevant approval, infrastructure budget and release controls | Completely separate from customer business-action approvals; this increment invokes none. |

## Minimal implementation patch, ready to assign

### A. Necessary common-service hardening

- Introduce transaction-aware task authorization/mutation helpers used by both task routes and the new action executor. For POST validate assignee by `(id, company_id, is_active)` and use the same transaction for insert plus any internal notification. For PATCH enforce tenant and current assignee/manager predicate in the mutation itself. Add `version BIGINT NOT NULL DEFAULT 0` to tasks and increment on every relevant change, including assignments/status/description. All touched mutation paths must use the service or a DB trigger must enforce version increments; otherwise the optimistic version is misleading.
- Route Lucy PTO through the existing validated service instead of direct INSERT. A later durable PTO adapter should accept an existing PoolClient so business result + action receipt commit together. Do not double-open transactions for that future adapter.
- Share role/capability classification on touched paths; preserve deny-by-default for unknown roles. Match direct Lucy project reads to accessible project search and assert tenant consistency on related-record joins. Do not reuse global company-wide project listing as the employee authorization oracle.
- Do not describe the existing create_task/PTO/payroll paths as newly hardened against model-origin intent until each is moved behind the same intent-bound executor. Either keep them explicitly labeled legacy sync behavior with tested restrictions, or stage migration separately; do not quietly broaden their scope.

### B. Separate deterministic action lane

Add a separate `lucy_action_requests` table and service, not a write mode in `lucy_background_work`. Start with exactly `task.set_status`; deny all other kinds. One action/request, no loops, arbitrary SQL, shell, HTTP, model calls, or recursive job creation.

Strict API example: `POST /api/lucy-v2/actions` with `{requestKey, action:"task.set_status", taskId, expectedVersion, status}`. Status is pending/in_progress/completed; reject unknown fields, malformed IDs/types and absent requestKey. Derive company/user/current role from authentication, never body arguments. Bind a canonical versioned hash of action, tenant, actor, target, expected version, requested status and relevant authority revision. A duplicate key with the same payload returns original action; a changed payload conflicts.

Provide GET/list and cancel for these action requests, with identical scoped access checks. Reuse the existing limits as an upper bound initially (10 outstanding and 50 submissions/day/user), with company-level limits if required; enforce under lock. A separate kill switch controls this action lane only. Research-mode switches never enable writes.

Entry channels: an explicit task action button/form in Lucy; optionally an exact deterministic current-message command such as `Set task <uuid> to completed`. A model may suggest a task/status candidate but cannot submit an authorized command by itself. Freeform ambiguous language gets a customer-specific task choice/preview, not Samuel review. This initial typed/selected path is the actual permission-bearing user instruction.

Rows need: ID, company/user, role and authorization revision, request key and canonical hash, action/version, validated payload, target snapshot/version, origin channel/message/request ID (when present), policy revision/decision, optional exact approval reference, state, submitted/started/completed DB timestamps, result target ID/version, bounded sanitized receipt and error code. Unique `(company_id,user_id,request_key)`, strict state/JSON size constraints, tombstones retained. Never store credentials or raw provider errors.

### C. Atomic execution and cancellation

Use a short **single PostgreSQL transaction**, no external awaits except this transaction's SQL. Lock authoritative tenant/actor/policy/action/target rows in a consistent documented order. Revalidate current company active status, actor active status, password requirement, role/capability, subscription/complimentary entitlement, task membership/assignment/version, exact requested operation, policy revision and any unconsumed approval under those locks. Refactor entitlement readers to accept the transaction client; the current global-pool precheck alone is not an atomic fence. Complimentary sponsor membership/role must be included when it supplies entitlement. Relevant admin changes must use conflicting row locks or revision fencing.

Then mutate task status with tenant/assignee/version conditions, update action to completed with exact changed IDs/versions and receipt, append audit event, and commit together. If receipt/audit insertion fails, roll back the task mutation. A no-op current desired status is explicitly `already_satisfied`, not a fabricated new change. Expected-version conflict is a conflict, not permission to overwrite.

Cancellation and execution compete on the same action row: cancellation that wins first prevents mutation; completed execution that wins first remains completed and returns its receipt. Cancel never erases a committed receipt or silently undoes business records. No lease is needed around this short DB-only execution; worker selection may use `FOR UPDATE SKIP LOCKED` inside the execution transaction. An interrupted uncommitted transaction rolls back; a committed action carries its completed receipt. On uncertain COMMIT, reconnect and inspect that same action ID; never create a new key or blindly rerun.

Keep the original chat request ledger for conversation replay and correlate it with action IDs, but do not reuse `processing` or `uncertain` chat records as approval. New mutation requests always require their own durable request key.

### D. Organization autonomy policy without prompt authority

Create a small versioned tenant policy table, never freeform prompt rules or Lucy preferences. Initially only rule fields for `task.set_status`: permitted principal category (employee-assignee or manager-group), scope enum (assigned/current-company), allowed status transitions, mode `execute_on_request | confirm_requester | deny`, optional expiry and bounded rate limits. Defaults mirror existing task permissions and execute on explicit request. Rules can narrow existing capability, never elevate it. No `always_allow_anything` wildcard and no support/provider permissions.

Only the explicit policy-settings API accepts changes from `manage_lucy_policy` actors, with expected revision and audit. A rules version supplied by a client/model is not authoritative; load it from DB. Unknown action, role, mode, malformed rule, stale version or unavailable authorization fails closed. Store presentation preferences separately, unchanged.

If mode is `confirm_requester`, create a customer action proposal bound to canonical payload, target version, actor, tenant, policy revision and expiry. Confirmation names that action ID/hash through the UI, not the most recent conversation “yes”. Consume approval in the same transaction as the write. Changed target/payload/policy or expired/revoked approval requires a new proposal. Delegated organization-manager approval is a later policy mode: verify the approver's current tenant and explicit approval capability, and bind both identities. Do not approximate it by routing everything to Samuel.

For durable queued actions, role-string equality is insufficient after revoke-and-restore. Add an authorization revision/generation changed by relevant user/company access changes, and compare the captured revision on execution. Actor deactivation, tenant movement, role changes, password reset policy, policy edits, explicit grant revocation and kill switch must prevent pending writes. Subscription expiry is checked against current DB time. Define the concurrency guarantee precisely: whichever authorized transaction acquires/commits the locked state first wins; do not promise cancellation can undo an already committed action.

A policy allowing execution on request is **not** permission for Lucy to invent tasks. Future self-initiated workflows need a separate explicit standing mandate with enumerated trigger, actions, target selectors, limits, expiry, schedule and revocation. Retrieved text, task descriptions, model output and conversation memories can never create or modify that mandate.

## Threat model and required defenses

| Threat | Required defense / verification |
|---|---|
| Guessed tenant/user/action/task IDs; forged role or approved flag | Server-derived actor; exact tenant predicates on every lookup/mutation/history read; strict body rejects authority fields. Foreign IDs yield generic unavailable response. |
| Employee accesses unassigned work or tenant manager crosses company | Target capability check inside transaction; related-record tenant assertions; test deliberately inconsistent references. |
| Role changes/revoke-and-restore while queued; expired subscription | Live transactional authorization plus captured revision, current entitlement/expiry and policy revision; old queued intent does not resurrect. |
| Prompt injection from task names, documents, old history, malicious model tool calls | Read-only proposals; no model-accessible executor or policy editor; typed authenticated current action is authority; taint every free-text read if legacy write runtime remains. |
| Changed task after preview/approval | Target version and exact payload hash; conflict response, no broad “latest proposal” approval. |
| Double clicks, retries, two workers, response/COMMIT loss | Unique request identity; business result/receipt/audit in one transaction; same-ID reconciliation; no retries based only on missing response. |
| Cancel races; worker dies; audit failure | Same-row lock arbitration, atomic write and receipt, transaction rollback; completed records remain truthful. |
| Tenant admin misconfiguration / privilege escalation | Policy intersects code-level capabilities and fixed action registry; explicit policy admin capability; no wildcard grants; revisioned changes. |
| Privacy leak via “unified activity” or guessed links | Permission-filtered projection per domain; never union raw support/global logs into customer feeds; recheck source access when opening evidence. |
| Quota abuse / provider spend / code-repair escalation | One bounded DB action, per-actor/company limits, no provider/browser/shell/payment imports; distinct principal types and registries. |

## Visible Lucy activity history: feed from receipts, not model narration

Add a normalized **read projection**, not a shared authority system. Each event carries domain, tenant (if applicable), action/run ID and correlation IDs, actor identity safe for that viewer, action kind, phase/status, DB recorded timestamp, actual observed start/end timestamps when known, exact outcome, and typed evidence references. Record `unknown` when execution or deployment cannot be verified. Requested/queued is not started; test passed is not deployed; build succeeded is not store submitted or approved; diagnosis/proposal is not a completed fix. Historical best-effort command_events entries must be labeled legacy/unverified, not silently upgraded to receipts.

- Customer task/PTO/etc actions: durable action receipt and transactional audit are canonical. Employees see their own or currently accessible assigned-work activity; managers see only their company; sensitive/payroll categories retain separate permission checks. A task's history must not expose prior inaccessible companies or unrelated private request text after assignment changes.
- Research/diagnosis: current work records supply queued/running/completed/partial/cancelled plus their evidence. Model conclusions are labeled diagnosis, not asserted system changes.
- Repair/test/build/deploy/submission: project verified events from the existing support/release pipeline only. Preserve commit SHA, CI/run/build/deployment/submission IDs, actual stage status and timestamps, and verified links/artifacts. Source stage events should have unique `(domain, source_id, event_id)` identities so repeated polling does not duplicate history. No invented times when only a polling observation time is known; show observedAt separately.
- Support-owner timeline is authenticated with support authority; customer timeline with CompanyActor. A customer tenant `owner` must never gain access to platform-owner logs merely because role strings match. Current separation is explicit in [ownerOperationsRoutes.ts:4–11](https://github.com/Samuelwedi/future-jobs-pro-ai/blob/71ec27a0b62f34c9754c9a2dfbf4effcb475040c/backend/src/routes/ownerOperationsRoutes.ts#L4-L11).
- If a customer should see a repair that affects them, publish a deliberately sanitized tenant-linked incident/release status projection. Do not expose raw support notes, all-customer diagnoses, credentials, internal prompts, CI secrets or unrestricted log URLs. Evidence links need authorization at open time, not only when the event is stored.
- First patch should produce receipt fields and safe per-user/per-company action-list API that this history can consume. UI and cross-domain event adapters are separate implementation assignments.

## Acceptance tests before enabling the new action

1. DB integration: employee-own-task succeeds; unassigned/other-employee/other-company denied; each manager alias succeeds only within tenant; unknown role denied. Include inconsistent task assignee/project/user references and moved users, not just valid fixture graphs.
2. Domain parity: task POST rejects foreign/inactive assignee; direct UI and Lucy use same authorization; Lucy PTO matches real-date/type/range/overlap service behavior. No employee receives all company projects via alternate Lucy read tools.
3. Input/intent: reject missing keys, unknown JSON fields, `companyId`, `userId`, `role`, `approved`, fake policy versions, extra action kinds, invalid task status/version. A malicious model can propose but never commit; instructions in every readable text field cannot authorize a write or change policy.
4. Replay: exact duplicate yields same result with one mutation/audit; key with different target/status/version conflicts; parallel submit and worker instances commit at most one mutation. Keep chat ledger legacy compatibility tests, but no untracked new actions.
5. Access races: disable user/company, change role/company, force password change, expire subscription, revoke complimentary sponsor, change rule, revoke then restore before execution. Pending action stays fenced. Recheck result access after revocation; do not leak a cached receipt.
6. Atomicity: injected failure before update, after business update, before receipt, before audit, before COMMIT and ambiguous COMMIT. No mutation without its receipt/audit. Reconciliation returns the committed receipt or safe terminal uncertainty, not a new action.
7. Cancellation: before execution, concurrent with execution, after commit and repeated cancel. Winner semantics are deterministic; committed receipt survives and no false undo is reported.
8. Policy: only tenant policy administrators edit; managers/employees cannot self-authorize; stale expected revision conflicts; expired/denied/malformed rules fail closed; policy cannot grant support/payroll/payment/provider/build capabilities. Confirmations are action-specific, tenant-specific, expire, single-use, and do not authorize changed payloads or targets.
9. History: employee/manager/support-owner separation, moved-user protection, sensitive-event redaction, pagination with stable cursor, bounded receipts, duplicate external events, truthful unknown/partial states, and evidence-link access checks.
10. Isolation: poison-import tests prove the task-status executor cannot import provider/inference, browser, shell, payment, support repair or legacy general dispatcher; old research modes remain read-only and their kill switches independent. Migration reruns/rollback and deployed-schema upgrade tests.
11. Use independent connections in a local PostgreSQL integration fixture for locks/concurrency/COMMIT uncertainty. Existing single-session PGlite coverage is useful but does not prove multiprocess linearization. Do not connect production.

## Implementation addendum: prerequisite hardening only

- Lucy PTO now uses `createPTORequest`, preserving the route's live actor/entitlement checks and adding the service's real-date, type, range, overlap and locked membership checks. Optional expected-role checking is supplied by both touched HTTP callers; prior service callers remain compatible.

Old proposals with missing company attribution must be prepared again. The current exact-customer payroll confirmation remains; no Samuel approval was added.
